# ADR-004: Implementación de Pruebas Unitarias en el Pipeline de CI/CD

**Fecha:** 2025  
**Estado:** Aceptado e implementado  


---

## Contexto

Como parte de la implementación del pipeline de Integración Continua (CI/CD), se identificó la necesidad de incorporar pruebas automatizadas que permitieran validar la lógica de negocio del proyecto en cada cambio realizado al repositorio.

Debido al tiempo disponible y al alcance de la entrega, se decidió priorizar las clases con lógica de negocio pura y sin dependencias de infraestructura, facilitando la creación de pruebas unitarias confiables y de fácil mantenimiento.

---

## Decisión

Se implementó un proyecto de pruebas unitarias utilizando **xUnit** (`CitasApp.xUnit`) y se configuró el pipeline de GitHub Actions para ejecutar automáticamente todas las pruebas en cada *push*.

Las clases seleccionadas fueron:

| Clase | Archivo de pruebas | Cantidad de pruebas |
|--------|--------------------|--------------------:|
| `TemporizadorPomodoro` | `TemporizadorPomodoroTests.cs` | 15 |
| `CatalogoFondos` | `CatalogoFondosTests.cs` | 8 |
| `FondoVideo` | `CatalogoFondosTests.cs` | 8 |

En total se implementaron **31 pruebas unitarias**.

---

## Justificación

Las clases fueron seleccionadas porque contienen lógica de negocio que puede verificarse de forma aislada, sin necesidad de utilizar *mocks* o depender de servicios externos.

- **TemporizadorPomodoro:** implementa el patrón State y permite validar las transiciones entre los estados del temporizador.
- **CatalogoFondos:** contiene lógica de búsqueda y selección del fondo predeterminado completamente independiente de infraestructura.
- **FondoVideo:** genera dinámicamente la URL de la miniatura de YouTube mediante una propiedad calculada, lo que facilita su validación mediante pruebas unitarias.

---

## Alternativas consideradas

Se evaluó escribir pruebas para `IAController`; sin embargo, este componente depende de `IHttpClientFactory` e `IConfiguration`, por lo que requiere la configuración de *mocks* y un mayor esfuerzo de preparación.

Dado que el objetivo principal era incorporar pruebas automatizadas al pipeline de CI/CD, se decidió posponer estas pruebas para una futura implementación de pruebas de integración.

---

## Consecuencias

### Positivas

- La lógica de negocio crítica se valida automáticamente en cada ejecución del pipeline.
- Se reduce el riesgo de introducir regresiones durante el desarrollo.
- Se establece una base para ampliar la cobertura de pruebas en futuras iteraciones.
- La integración continua proporciona retroalimentación inmediata sobre posibles errores.

### Negativas

- La cobertura actual se limita a clases sin dependencias externas.
- Los controladores y servicios de infraestructura aún no cuentan con pruebas automatizadas.

---

## Estado

El workflow de **GitHub Actions** ejecuta automáticamente las **31 pruebas unitarias** en cada *push* realizado al repositorio.

**Resultado actual del pipeline:** ✅ Success.
