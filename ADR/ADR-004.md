# ADR-004: Evolución de Persistencia, Acceso a Datos, Funcionalidades y Seguridad de Configuración

## Estado
Aceptado

## Contexto
Tras la adopción del estilo N-Layer (ADR-01) y su justificación formal (ADR-03), el desarrollo de Gnosis avanzó hacia una fase de implementación real que expuso cuatro necesidades concretas, no previstas en el detalle de las decisiones originales:

1. La cadena de conexión inicial dependía de **SQL Server LocalDB**, atada al entorno Windows/Visual Studio del desarrollador, lo que limitaba la portabilidad.
2. El proyecto mantenía interfaces de repositorio específicas por entidad (p. ej. `ITareaRepository`) que **nunca se registraron ni se usaron** — código muerto que ocultaba, además, que el controlador de Tareas devolvía datos simulados en lugar de reales.
3. Se identificó la necesidad de dos funcionalidades nuevas: una **Agenda** de bloques de tiempo vinculables a tareas, y un **Dashboard** de productividad que visualiza el progreso histórico del usuario.
4. `Gnosis.WebApi/appsettings.json`, versionado en un repositorio público de GitHub, llegó a contener en texto plano la contraseña real de la base de datos.

Las cuatro decisiones siguientes se agrupan en un solo ADR porque ocurrieron en la misma etapa de evolución del proyecto y están relacionadas entre sí: todas dependen de (o ponen a prueba) la abstracción de persistencia definida en ADR-01/03.

## Decisión

### 1. Migración del motor de persistencia a PostgreSQL (Npgsql)
Se migra la persistencia de SQL Server LocalDB a **PostgreSQL**, usando el proveedor **Npgsql.EntityFrameworkCore.PostgreSQL** sobre el mismo `GnosisDbContext` y el mismo modelo de entidades (`Tarea`, `SesionEnfoque`, `BloqueTiempo`). Se generan las migraciones de EF Core correspondientes (`InicialConBloquesTiempo`, `AgregarFechaCompletadaYDashboard`).

### 2. Adopción exclusiva del Patrón de Repositorio Genérico (`IRepository<T>`)
Se estandariza el acceso a datos exclusivamente a través de un repositorio genérico, registrado una sola vez:

```csharp
services.AddScoped(typeof(IRepository<>), typeof(EfRepository<>));
```

Todos los servicios de negocio (`TareaService`, `BloqueTiempoService`, `SesionEnfoqueService`, `EstadisticasService`) dependen únicamente de esta abstracción genérica. Se elimina el uso de `ITareaRepository`.

### 3. Extensión funcional: Agenda (Bloques de Tiempo) y Dashboard de Productividad
Se agregan dos features siguiendo el mismo patrón N-Layer ya establecido:
- **Agenda:** entidad `BloqueTiempo` (FK opcional a `Tarea`, `OnDelete: SetNull`), CRUD completo en `BloquesTiempoController`, panel `PanelAgenda.razor` con vista semanal y arrastrar-soltar nativo (HTML5 Drag and Drop, sin JS interop adicional).
- **Dashboard:** servicio `EstadisticasService` que agrega sesiones de enfoque y tareas completadas por día/semana (incluye racha), expuesto en `EstadisticasController`, visualizado en `PanelDashboard.razor` con una gráfica de barras en CSS puro. Se añade el campo `Tarea.FechaCompletada`.

### 4. Gestión de configuración sensible fuera del control de versiones
`appsettings.json` (versionado) conserva solo un **placeholder** (`Password=CHANGE_ME`). `appsettings.Development.json` contiene la cadena de conexión real y se excluye del control de versiones vía `.gitignore`, aprovechando que ASP.NET Core carga automáticamente el archivo de configuración específico del entorno.

## Justificación Técnica

1. **Portabilidad (decisión 1):** PostgreSQL es multiplataforma y de uso libre, reduciendo la dependencia de un stack exclusivamente Windows.
2. **Validación práctica de la arquitectura (decisiones 1 y 2):** gracias a la abstracción `IRepository<T>` propia de N-Layer, tanto el cambio de motor de base de datos como la eliminación de repositorios específicos **no requirieron modificar `Gnosis.Business` ni `Gnosis.WebUI`** — confirmando en la práctica lo decidido en ADR-01/03.
3. **Eliminación de deuda técnica silenciosa (decisión 2):** las interfaces específicas por entidad realizaban operaciones CRUD equivalentes sin lógica particular que las justificara, y su desuso ocultaba un bug real (datos simulados en el `GET` de Tareas).
4. **Reutilización sin regresión (decisión 3):** construir Agenda y Dashboard sin tocar código de Pomodoro, Audio o IA cumplió el objetivo explícito de no romper funcionalidad existente. Drag-and-drop nativo y CSS puro evitaron dependencias de terceros.
5. **Uso de mecanismos nativos de la plataforma (decisión 4):** ASP.NET Core soporta nativamente la superposición de configuración por entorno (`appsettings.{Environment}.json`), evitando introducir un mecanismo adicional (Secret Manager, Key Vault) para resolver el problema en el alcance actual del proyecto.

## Alternativas Consideradas y Descartadas

### 1. Mantener SQL Server LocalDB
* **Por qué se consideró:** era la configuración inicial del proyecto y no requería ninguna migración.
* **Por qué se descartó:** ata el entorno de desarrollo a Visual Studio/Windows y complica un futuro despliegue multiplataforma.

### 2. Mantener un repositorio específico por entidad
* **Por qué se consideró:** permite añadir métodos de consulta muy particulares a cada entidad sin "contaminar" una interfaz genérica.
* **Por qué se descartó:** en la práctica llevó a interfaces (`ITareaRepository`) sin registrar ni usar — deuda técnica silenciosa que ocultaba un bug real de datos simulados.

### 3. Librería de charting de terceros para el Dashboard
* **Por qué se consideró:** ofrece gráficas más ricas (tooltips, animaciones, ejes configurables) que una implementación propia.
* **Por qué se descartó:** el alcance del Dashboard (barras simples por día de la semana) no lo justificaba; una gráfica en CSS puro evita una dependencia adicional en el cliente Blazor WASM.

### 4. Variables de entorno o Secret Manager de .NET para las credenciales
* **Por qué se consideró:** es la práctica recomendada para producción y evita cualquier secreto en disco.
* **Por qué se descartó** (por ahora): añade pasos de configuración adicionales fuera del flujo estándar de `dotnet run` / Visual Studio para un proyecto académico en fase de desarrollo local; queda anotado como mejora pendiente antes de un despliegue real.

## Consecuencias

* **Positivas:** entorno de desarrollo reproducible en cualquier máquina con PostgreSQL local; cada entidad nueva obtiene persistencia funcional sin escribir un repositorio dedicado; Agenda y Dashboard quedaron aislados por capa sin afectar Pomodoro, Audio o IA; el repositorio público ya no expone credenciales reales.

* **Negativas / riesgos asumidos:**
  - Se introdujo una clase de bug recurrente (manejo de `DateTimeKind` con Npgsql) ausente en SQL Server/LocalDB.
  - Al no existir validaciones específicas por entidad en el repositorio genérico, la integridad referencial depende enteramente de que la capa de negocio envíe identificadores ya persistidos — causa raíz de una violación de llave foránea real (`FK_BloquesTiempo_Tareas_TareaId`), documentada como riesgo en la Evaluación ATAM.
  - Cada feature nueva (Agenda, Dashboard) tocó los cinco proyectos de la solución — el costo de modificabilidad de N-Layer se pagó en volumen de archivos (ver trade-off en la Evaluación ATAM).
  - La contraseña ya expuesta en commits anteriores del historial de git sigue siendo recuperable desde ese historial hasta que se rote la contraseña real de la base de datos.
